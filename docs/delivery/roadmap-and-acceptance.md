# 交付路线与验收规则

范围与阶段技术门槛沿用[需求第 9、10 节](../requirements.md)，不在此复制数值或另定产品路线。[当前状态](status.md)记录实际实现。

当前已按[M0 计划](m0-plan.md)完成 Go 核心、双宿主、四信令和工作台。2026-10-11 用户确认 P6 可采用显式兼容模式，UDP/TCP 的独立原字节、应用结果和清理均通过，本轮 M0 退出完成。标准模式的对端拒绝、历史失败及标准差异见[实施证据](../evidence/m0-implementation.md)和[兼容文档](../compatibility.md)。后续完整交付仍覆盖原需求的适用范围。

## 验收映射格式

每个进入实施范围的需求记录：需求 ID、标准条款/产品依据、设计位置、测试 ID、前提、操作、预期、失败边界、实现位置、执行版本、证据和状态。一项需求可对应多个用例，缺项不能留空后宣称覆盖。

用例定义与执行结果分开：计划可写预期；证据用 passed、failed、not-run、blocked。已有 LAB 编号保持稳定。M0 子集已有执行矩阵，不声称完成全标准追踪。

## 退出条件

工程交付需要实现存在、相关自动门禁通过、文档一致、必要审查和无未处理核心缺陷。真实设备互通、容量、真实密码产品及用户体验分别验收，缺环境不得用自模拟或静态检查替代。人工检查保持在 USER-ACTIONS，不阻断无依赖工程推进。

本次 M0 采用用户要求的单 Agent 实施、自检和自审路径，独立 Agent 审查为 not-run。兼容互通只关闭本轮明确的 P6 范围，不关闭 M5 的严格业务/安全符合性、两个独立实现来源、媒体、密码产品或发行门槛。

## 开发协作与验收的关系

A 按[协作流程](../dev-rules/development-workflow.md#agent-handoff)一次规划完整里程碑/明确子阶段，B 连续实施、自检和修复，A 集中复核；工作包不是逐批许可。先贯通已承诺基本功能，再由有明确承接的 LOOP 改进，不能把当前必需功能延期后宣称 MVP 完整。

工程交付、B 自检、收尾自审、A 独立审查、用户主观体验、第三方互通和发布分别判断。用户明确单 Agent 时由同一执行者完成自审，默认 A/B 分工不额外增加独立审查门槛；未发生的独立审查仍记 not-run。用户人工偏好可顺延，不自动阻断已有授权的技术工作或请求远端授权。但必需自动测试、协议互通和已知核心缺陷仍是对应阶段门槛，不能改成人工待办豁免。集成建议核对目标分支实际包含的前置范围，文档通过不覆盖产品失败。

初版工作台的视觉依据为 [UI-WORKBENCH-001](../design-rules/DESIGN.md#initial-ui-reference)，后续 UI 变更按真实版本核对布局与交互；本次登记未产生界面通过结论。M0 与完整 M1—M5 的产品范围不变。
