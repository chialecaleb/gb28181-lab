# 架构与公共契约规则

具体架构以[设计正本](../design.md)为准。Go 核心、React/TypeScript、Windows Wails 和 Linux Web 是现有需求基线；版本和第三方实现尚需开发时验证。

## 边界

桌面、HTTP、CLI、MCP 复用同一应用服务、权限与资源治理。协议核心不得依赖 UI 或宿主绑定；媒体工作进程、存储和密码提供器经接口隔离。禁止让 MCP 或内部平台绕过 GB 协议路径来冒充互通。

公共契约写清身份、版本、输入/输出、错误、权限范围、幂等、超时、取消、事件次序、副作用和清理责任。DTO 需要运行时校验，类型声明不代替边界检查。长任务固定输入和版本，拒绝已取消或旧代次的晚到结果；队列、缓存和媒体句柄有界。

修改接口同时核对所有消费者；存储迁移说明备份、失败恢复与兼容策略。未知字段和不支持能力的行为必须明确，不静默成功。模块规格按[模板](../templates/module-spec.md)记录到当前需要的深度。

## 开源选型

新增通用能力前先查官方仓库、文档和发行资料，记录查询日期、版本、维护状态、平台支持、许可、适配边界与退出成本。比较最适合的现成方案和必须自研的最小部分；不能凭记忆宣称活跃，也不为凑候选编造比较。

协议、编解码、密码和数据库实现优先采用成熟可维护能力，通过适配层集成。缺少符合条件的库时记录证据和自研边界。候选可用、已集成、已通过互通和已通过容量测试分别记录；上游单元测试不能代替本项目集成验证。

长期选择用 ADR；纯文档修正无需重新选型。上游问题提供合成最小复现，查已有修复后验证；向上游发送消息或上传资料依照会话授权。
