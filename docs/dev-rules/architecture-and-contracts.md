# 架构与公共契约规则

具体架构以[设计正本](../design.md)为准。Go 核心、React/TypeScript、Windows Wails 和 Linux Web 是现有需求基线；已验证版本见[技术栈](../tech-stack.md)，新增组合仍需真实验证。

## 边界

桌面、HTTP、CLI、MCP 复用同一应用服务、权限与资源治理。协议核心不得依赖 UI 或宿主绑定；媒体工作进程、存储和密码提供器经接口隔离。禁止让 MCP 或内部平台绕过 GB 协议路径来冒充互通。

公共契约写清身份、版本、输入/输出、错误、权限范围、幂等、超时、取消、事件次序、副作用和清理责任。DTO 需要运行时校验，类型声明不代替边界检查。长任务固定输入和版本，拒绝已取消或旧代次的晚到结果；队列、缓存和媒体句柄有界。

修改接口同时核对所有消费者；存储迁移说明备份、失败恢复与兼容策略。未知字段和不支持能力的行为必须明确，不静默成功。模块规格按[模板](../templates/module-spec.md)记录到当前需要的深度。

## 开源选型与角色责任

新增通用能力前先查官方仓库、文档和发行资料，记录查询日期、版本、维护状态、平台支持、许可、适配边界与退出成本。比较最适合的现成方案和必须自研的最小部分；不能凭记忆宣称活跃，也不为凑候选编造比较。

A 在制定推荐前完成上述查证，不把首次技术研究留给 B。维护判断结合归档状态、有意义的提交、发行及相关问题的响应，不以 stars 或统一“若干天内发版”代替依据；访问受限时如实记录，不能声称已确认。B 在实施时核对版本变化，再补构建、生命周期、兼容与打包实证。未变化的有效研究可以引用，纯文档纠错不重复选型。

协议、编解码、密码和数据库实现优先采用成熟可维护能力，通过适配层集成。缺少符合条件的库时记录证据和自研边界。候选可用、已集成、已通过互通和已通过容量测试分别记录；上游单元测试不能代替本项目集成验证。

通用能力自研仅在候选缺失、关键契约、许可、平台或维护风险有实证时扩大；说明不采用原因、最小范围与再评估条件。既有已验证实现不为流程同步整体推倒。安装和可逆集成按已有开发授权继续，文件处于 proposed/draft 不自动产生审批节点；真正改变产品、不可隔离的数据语义、授权或费用时才登记用户事项。

每项通用能力接入建立两层证据：上游独立最小样本验证引擎行为，本项目集成场景验证身份、权限、取消、恢复与实际使用方。第三方对象和版本留在适配层，优先官方 API/扩展点或最小补丁，不因复用而永久复制整个上游。

疑似上游问题先构造合成最小复现、固定版本、记录预期/实际，再查官方已有问题或修复版本。区分引擎、适配器、本产品规则和样本限制；升级/小补丁验证后记录来源、负责人和移除条件。非阻塞问题由 LOOP 承接，当前必需缺口仍由 Agent 解决。公开 issue、评论、PR 或上传证据属于外部动作，先准备具体材料，再按会话授权执行。

长期选择用 ADR；纯文档修正无需重新选型。已确认选择不重新列为用户待决定，B 补实际组合验证，A 或单 Agent 自审者核对证据与适用范围。
