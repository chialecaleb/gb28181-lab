# Agent 开发流程

默认协作是 **Agent A 规划 → Agent B 连续执行 → Agent A 集中审查**。用户处理决定、人工检查和授权，与 Agent 开发分别推进。本文是职责与交接正本；用户事项写法见[沟通规则](communication.md)，版本保存见[Git 规则](git-and-github.md)。用户要求一人全部完成时使用[单 Agent 路径](#single-agent)，当前任务的明确要求优先于默认分工。

## 开始与范围

先按 [AGENTS](../../AGENTS.md)确认目标、实际分支/提交和已有改动，读取导航、状态、用户事项及受影响正本。脏工作区、提交指纹变化或尚未合并本身不是阻塞：先判断差异、所有者和依赖，不自动 stash/reset 或覆盖他人文件。

一个阶段指一个里程碑或已明确划出的子阶段。A 的计划一次覆盖这个阶段的全部工作、必需前置、关键失败路径、验证、修复、审查和退出条件，不把已承诺范围拆成等待用户逐批确认的多份计划。工作包可按依赖排序，但不是新阶段或许可节点。普通细节留给 B；只有独立验收、维护或回退确有需要时才划出子阶段。

同一阶段使用唯一计划、一份交付报告和其中可辨识的审查记录；默认由 B 写交付、A 写审查，单 Agent 则明确写实施者自审。确需独立报告时引用原计划和交付报告。已有同等材料直接复用，小修可由任务说明承载。换会话、返工、上下文切换不另建竞争正本。prompt 只指定角色、文件、版本和本轮动作，不复制另一份范围；文件的复用和退役见[材料生命周期](../governance/documentation-policy.md#stage-documents)。

<a id="continuous-execution"></a>
## 连续执行与用户参与

除任务明确限制外，开发授权覆盖常规本地实现、已选依赖安装、定向验证、失败修复、文档同步和归属明确的分支准备、暂存与 commit/amend，Agent 连续完成这些工作。已有授权持续有效，不按文件、工作包或测试轮次重复询问。用户中途补充默认是本轮修正，回写相关计划/决定和证据范围后继续；状态询问简短回答后恢复工作，不默认重启整个流程。

| 情况 | 执行方式 |
| --- | --- |
| 需求和边界已定，属于常规实现、验证、修复或版本保存 | Agent 自主完成，失败先修复，再继续下一步 |
| 尚需偏好或候选定稿，但存在符合约束的可逆方案 | 采用推荐默认值，登记当前默认、影响和证据；未答复不写成用户已确认 |
| 缺外部权限、配置或必需决定 | 先核对已有授权并完成诊断、可控验证；仅在下一动作确实依赖且无法合法隔离时暂停该部分 |
| push、PR、合并或发布尚无相应授权 | 先完成具体可审阅成果；登记动作、目标、依赖与范围，继续已获授权且无依赖的本地工作 |
| 缺实现或自动检查失败 | 由 Agent 修复；不得改成人工待办、降低断言或包装成可延期问题 |

真实阻塞要同时满足：下一动作确实依赖缺失的决定、数据语义或授权/配置；没有符合现有约束的可逆替代。先完成诊断和可审阅方案，说明具体动作、依据及受影响范围，只暂停依赖部分。工具或执行环境确实要求确认时，说明限制来源；文件名、模板状态和希望更稳妥本身不产生审批节点。

两条工作线分别是：

- Agent：完整计划 → B 实现/自检/修复 → 交付版本 → A 审查/局部修复或集中返工 → 在授权范围内集成。
- 用户：集中事项登记 → 在合适时间按编号答复或检查 → Agent 回写决定/结果、修复并安排必要复测。

用户事项仅在 [workspace 唯一入口](../../USER-ACTIONS.md)维护，不按阶段催批；非阻塞项可跨阶段顺延。待做的主观检查不自动阻断技术工作或请求远端授权。必须执行的协议互通、数据恢复、安全或自动测试仍按阶段门槛处理，不能因叫作“用户事项”而豁免。

<a id="agent-handoff"></a>
## A / B / 用户职责

| 角色 | 应完成的工作 | 交出什么 |
| --- | --- | --- |
| A 规划 | 核对完整阶段范围、实际代码和决定；先查证开源候选；定义依赖、数据/授权、风险、失败路径、验证和收尾 | B 可直接执行的唯一计划、官方依据、基点、需保留项、事项编号与可复制 prompt |
| B 执行 | 核对现场与授权，复用或准备基线/分支；连续完成实现、自测、修复、文档和交付提交 | 任务/需求→实现位置→实际验证→状态/限制的报告，源码与产物、版本和剩余责任 |
| A 审查 | 对照同一计划、交付版本和真实实现核实成功/失败路径；复用有效证据、补必要验证，直接修复明确局部问题 | 审查结论、已修复项与复验；需 B 持续编码的较大缺口一次性列完整 F 清单 |
| 用户 | 决定产品取舍、处理不可替代的真实条件、主观体验和外部动作授权 | 按集中事项编号给结果，无需替 Agent 补代码/测试、排障或整理报告 |

A/B 是开发职责，可对应不同工具或会话，和产品内 API/MCP 权限无关。上述流程不授权自动启动其他 Agent、创建聊天或发送消息。默认同一工作区同一时间只有一个写入者；明确要求并行时才安排隔离目录、文件归属和验证责任。

不能把 B 自检改名为 A 已审核，也不能把 A 技术审查写成用户已验收。已有单 Agent 记录保留其历史含义。

<a id="single-agent"></a>
### 单 Agent 完成全部职责

用户明确要求“由你全部完成”、不交给另一 Agent 或同一 Agent 兼任时，当前 Agent 先完成 A 的完整规划，再连续完成 B 的实施/自检，最后按[评审口径](../../REVIEW.md)单独复核最终差异并修复、复验、更新报告和保存版本。职责切换不需要用户再次说“继续”，不能在计划完成或 B 自检后就以默认交接为由结束任务。

报告区分实施自检与收尾自审，记录实际范围、问题和证据；独立 A 审查标为 not-run，并说明本任务采用单 Agent。默认流程不再另加一次独立审查作为退出条件，也不冒称它已经发生。若当前任务或适用门槛明确要求独立审查，再如实保留该项；单 Agent 要求不豁免必需测试、安全边界或用户独有的决定与权限。

自审发现较大缺口时仍由当前 Agent 在同一计划和授权范围内连续补齐，使用原问题编号记录修复与复验；不为角色形式启动其他 Agent。完成后直接报告整体结果和一个首选下一动作，不再提供需要用户执行的 A/B 内部交接。

### A 的完整计划与查证

计划包含：目标/非目标、基线和依赖分支、相关需求/条款、完整工作包、每包预期与关键失败、已有命令和待建检查、运行/资源/安全边界、需保留修复、收尾审查和退出条件。当前必需但尚未实现的前置直接纳入，不留给没有承接的“下一批”。阶段开始还要列出[文件与文档整理](../governance/documentation-policy.md#stage-cleanup)清单。

涉及技术选型或新增通用能力时，A 在推荐前按[开源规则](architecture-and-contracts.md#open-source-first)查官方来源、日期、发行/维护、许可和适配证据，明确自研最小范围与替代方案；不能凭旧记忆指定实现或把首次调研全部留给 B。B 再验证实际组合、取消/恢复、打包和平台兼容。资料可用、已集成和验证通过分别记。

<a id="local-reference"></a>
A 规划和 B 实现功能前均按[本地参考规则](local-materials.md#local-reference)读取允许的索引；单 Agent 实施前复核规划时读取的索引及适用范围，有变化再补读。找不到如实说明并继续独立研究。LiveGBS 仍只在独立实现与合成验证后的受控测试阶段使用，流程复用不扩展资料用途。

### B 的实施与交付

B 先判断计划与现场是否兼容，保留已确认修复和他人工作；有差异就记录实际基点，不要求仅为开工重建干净仓库。正常流程、错误/超时/取消、资源释放、数据兼容和权限一起实现，受影响接口、使用方、规则、文档与测试同步。必要修复覆盖同类输入和状态不变量，不能只消除报告中的一个样本；检查范围按实际风险选择。

交付前对照完整计划自检并修复，不能只交演示、截图或“已完成”自述。报告记录真实命令、退出状态、样本口径、版本和产物，区别内部互测、独立向量、外部对端、媒体/密码产品和人工体验。证据按[质量门禁](quality-gates.md)核对源码、依赖、测试、样本、配置和环境的适用条件后复用，变动部分及新风险定向复验。

保存可审查版本后再交给 A；同阶段后续未推送修复按 [Git 规则](git-and-github.md#review-commits) amend，执行角色或轮次不是拆提交依据。报告与实现同次提交时使用测试基点或“包含本报告的提交”定位，最终消息给 commit，不为回填报告自身 SHA 制造循环提交。

### A 的集中审查与返工

A 先看实际版本、完整相关实现和需求，再判断 B 的证据是否支持结论，不只复述报告，也不无条件全量重跑。能确定且属于授权范围的局部修复由 A 当轮完成并复验；风格偏好不阻断，新愿望另记后续。

较大模块缺口、跨层恢复或多处耦合问题需要 B 连续实施时，A 先完成当前可独立的审查，再一次性交回确认的全部差异。每项使用当前报告内稳定 F 编号，写严重度、触发/实际、预期/依据、位置/证据、修复验收和状态。交接给当前基点及 A 已修复的保留项，不复制原计划或逐问题往返。

B 沿用原编号补修复位置与实际验证，无法完成给具体原因和受阻部分。“已处理”不算关闭。默认由 A 核实后关闭同一编号；单 Agent 由实施者自审核实并明确标注。改写本地提交后给新基点，原测试版本仍保留，不把历史整理写成重新测试。

<a id="agent-user"></a>
### 用户反馈进入当前工作

用户不需要阅读 A/B 计划和报告才能知道要做什么，具体动作与完整步骤只在[集中用户事项](../../USER-ACTIONS.md)维护，聊天按编号交流。接收答复的 Agent 当轮回写原意、适用版本与范围：决定更新正本，失败转为 Agent 修复，修后标待复测，授权只执行列明动作。有效答复不因换角色或会话重新待批；生命周期见[沟通规则](communication.md#item-lifecycle)。

<a id="mvp-loop"></a>
## 完整功能与后续循环

先贯通当前已承诺范围的基本使用链，再据反馈改进；不要等单模块所有风格/便利项清零才继续。但不得借 MVP 缩减 Lab 的完整需求、当前必需用例、标准边界、权限、数据和恢复要求。仍缺基本功能不能宣称 MVP 完成。

可延期问题必须不阻断基本使用、不破坏当前必需门禁或数据/权限/恢复，且有明确承接。Agent 侧 LOOP 记在[状态页](../delivery/status.md#followup-loops)，至少说明影响、替代办法、负责人、触发条件和复测入口。用户决定进入 Q 项；代码和自动测试缺口留给 Agent，不转嫁给用户。

<a id="next-step"></a>
## 每轮结束的首选下一步

最终交付说明当前职责完成什么、阶段判断、版本和报告入口，再给一个首选动作、依据和尚缺条件。不要让用户从长报告猜下一步，也不以推荐代替执行授权。

| 当前结果 | 首选下一步 |
| --- | --- |
| A 完成可执行计划 | 交 B 连续实施，附可复制 prompt，引用计划、基点/分支、保留项、验证和权限 |
| B 完成实现和自检 | 交 A 集中审查，附最终版本、报告及审查 prompt，不把自检当独立审查 |
| A 发现较大实现缺口 | 一次性交 B 返工，附 F 编号、全部差异、保留修复和定向复验 prompt |
| 单 Agent 已完成规划、实施、自检和收尾自审 | 直接交付整体结果；按真实依赖和授权推荐集成或下一任务，不再要求用户找另一 Agent 完成原任务 |
| A 审查收敛且当前工程门槛满足 | 在已有授权内集成；缺授权时在集中事项写明 push/PR/合并各自目标和范围，再推荐用户处理 |
| 远端已完成或用户暂不授权，且后续有合法基线 | 推荐下一阶段 A 规划，说明依赖和入口；只有任务已涵盖后续时才继续执行 |
| 用户答复事项或反馈失败 | 当前接收 Agent 先回写，A 汇总有效决定；能局部修的修复，较大编码交 B，修后标待复测 |

人工检查的完整步骤只在集中事项维护，聊天引用本轮新增、变化或需重测编号。同阶段尚有必需自动验证失败、未关闭核心缺陷或任务要求的审查未完成时，不推荐合并该阶段。合并建议还要检查[前置范围](git-and-github.md#integration-scope)，不能以文档阶段通过覆盖待合入的产品失败。单 Agent 自审任务按明确授权和实际边界报告，不虚构另一审查者。

## 完成和例外

交付必须有真实实现/文档、对应检查、自检闭环、准确状态和可恢复版本。工程完成、独立审查、用户体验、第三方互通、密码产品、性能和发布分别判断；缺环境不写成通过，纯文档不制造协议或设备实验。

必要例外注明原规则、触发、范围、依据、替代验证及失效条件；当前明确授权优先，例外记录本身不增加审批。已授权常规工作继续，只有确实依赖用户决定/权限的部分暂停。交接使用[统一模板](../templates/agent-handoff.md)，不依赖隐藏聊天记忆。
