# Git 与 GitHub 协作

## 仓库与版本

主分支 `main` 为经检查、合并的最新实现。workspace、hub、lab 独立提交和维护远程，无 submodule、gitlink 或组合版本锁。依赖和标准仍按实际版本锁定；“跟随 main”不等于安装浮动依赖。

初始化时的直推例外已经结束，不提供后续直推、重建历史或发布授权。当前操作按会话有效范围执行，流程文件不新增外部授权。

<a id="stage-commits"></a>
## 一个阶段一个分支、一个交付提交、一个 PR

阶段是里程碑或已明确划出的子阶段。首次本地交付保存一个可审查提交；同阶段规划、B 实施/返工、自审或 A 审查记录/局部修复和反馈修复，在推送前都归入这个提交。不按角色、轮次、代码/文档类型或工作包拆提交；不同阶段仍分别保存，不把未合并前置混入本阶段。获准远端交付后同阶段使用一个 PR，审查修复更新原 PR；只因新增一轮反馈不新开 PR。

| 动作 | 时机与条件 |
| --- | --- |
| 分支 | 已有同目标分支继续使用；独立阶段才建立新的 `codex/<目标>` 分支 |
| 本地 commit | 范围内首次交付、自检、必要文档和暂存核对完成；本地可审查不等于整阶段验收通过 |
| amend | 同阶段未推送的返工/审查/修复验证后，核实归属和共享情况再归入；消息描述最终结果 |
| push / PR | 当前 Agent 侧门槛满足、按任务要求完成审查，并有相应明确授权；集中提交一个完整批次 |
| 合并 / 发布 | 各自范围、检查及授权满足；合并与产品发布验收分别判断 |

中间检查点只为回退、试验分叉、中断或跨环境恢复需要建立，不由时间、测试轮次或工作包数量触发。未推送阶段交付前归并自己的检查点；WIP 必须标明未完成，不能作完成证据。已推送历史默认追加集中修复，不为整理外观自动强推。

<a id="branch-baseline"></a>
### 分支与依赖基点

开始检查 `git status --short --branch`、提交和跟踪关系；不自动 stash/reset 他人工作以凑干净状态。独立新目标通常从已核对的 main 建分支；若依赖尚未合并的阶段，先保留其可恢复提交，再从明确提交建立后继分支，交接写明依赖，不假称已来自 main。

前置阶段尚未 push/合并不阻断已有授权的本地后继工作，也不自动授权启动新阶段。前置 squash 合并后按实际差异整理后继分支并验证；涉及已共享历史改写时遵守额外授权。对前置阶段的修复回其分支处理，不 amend 到后继阶段。

已合并阶段收到新的反馈时，按新的修复任务或已明确阶段建立分支，引用原问题和被测版本；不能把“人工反馈归入阶段提交”理解为允许改写已合并历史。用户已授权的后续范围连续衔接，未授权的新阶段只给具体推荐。

<a id="integration-scope"></a>
### 集成前检查实际范围

推荐 push/PR/合并前同时核对阶段基点、实际目标分支及目标到交付版本的全部差异。阶段自身的一个提交与相对 main 的所有未合并提交是两个范围：前置未合并时，报告必须列出依赖和各自验证状态，不能将文档阶段通过解释为其包含的产品实现也已通过。

前置存在必需测试失败、未关闭核心问题或必要审查缺失时，不推荐把整条依赖链直接合入 main。先推荐解决真正依赖的工程缺口；只有可以形成不依赖该前置的独立完整变更时才另作集成方案，不能通过漏带文档/实现、掩盖失败或擅自改写历史绕过它。合法的本地后继工作仍可继续。

### 提交内容与检查

修改前确认文件归属，按路径或 hunk 暂存，再看 `git diff --cached`、`git diff --cached --stat` 和 `git diff --cached --check`。代码、使用方、迁移、文档与证据同次一致；不夹带私有配置、实际数据库、抓包、构建目录或他人改动。部分暂存时确认提交版本包含必要依赖，工作树通过不能冒充暂存版本通过。

消息用 feat/fix/docs/refactor/test/ci/build/chore 描述具体最终结果，复杂提交正文写原因、验证、兼容与限制。只有实际满足门槛才写“阶段完成”。本项目未新增 DCO、GPG、许可证或 hook 决定，不从流程参考材料推导法律声明或修改全局 Git 身份。

<a id="review-commits"></a>
### 审查修复与交接

A 在已授权范围内直接修复明确局部问题，验证后将未推送的同阶段修改和审查记录 amend 回阶段提交；B 返工同样处理。不以多建 fix 提交替代报告中的 F 编号和复验记录。较大缺口一次性交 B，收到证据后由 A 核实关闭。单 Agent 任务由当前 Agent 完成全部修复和自审，使用相同提交规则，不为虚构角色交接另加提交。

amend 或归并前核对远端引用、已有推送记录及协作状态；没有 upstream 不能证明从未推送。仅整理归属明确、未推送的本阶段历史，必要时先保留恢复点。若发布状态不清楚，先查明或追加修复，不冒险改写。改写后给接收方新基点；历史测试 SHA 保留为原证据，不把 commit 变化写成重新测试。

报告与实现同次提交时，报告写测试基点/源码指纹或“包含本报告的提交”，最终聊天给实际 SHA。阶段间的已有提交保持原样。远端备份只有 push 成功后才能声明；推荐另一 Agent 或给出 prompt 不会自动创建聊天或发送消息。

### 用户授权与人工检查

按当前任务完成 A 审查或单 Agent 自审、必需用例/自动证据通过且无当前核心阻塞后，再按实际集成范围推荐 push/PR/合并。缺哪项授权，就在[集中事项](../../USER-ACTIONS.md)登记具体目标、分支、前置依赖和动作；授权不按角色推导，push 不包含合并或发布。自审不冒充独立审批；明确的单 Agent 任务也不因默认分工再增加独立审查前提。当前任务明确要求只修改、不提交时优先遵守。

待做的主观检查、未答复的非阻塞偏好可以在用户事项中顺延，不自动成为远端授权前提；当前必需协议互通、数据恢复、安全和自动验证仍须满足。已知核心失败不能为了合并改为人工待办。产品发布另需相应测试范围与授权。

## PR 与主分支保护

[main.json](../../.github/rulesets/main.json)为期望规则；远端实际设置须核验，文件存在不等于生效。

| 设置 | 规则 |
| --- | --- |
| main 更新 | PR 合并；初始化结束后禁止日常直推 |
| 删除与强推 | 禁止 |
| 历史 | 线性，PR 只允许 squash |
| 强制审批人数 | 0，适合单维护者；自审不称独立审批 |
| Review 讨论 | 必须解决 |
| 必需检查 | `repository-quality`，绑定 GitHub Actions App |
| 更新到最新 main | 不强制每次 rebase；有相关冲突或依赖变化时仍须更新验证 |
| 绕过者 | 无常驻 bypass，包括管理员 |

推送、创建 PR、合并、发布依照当前任务已有授权，已授权不重复询问；不得把文档规则当作永久外部操作授权。需要新增授权时先完成可评审成果，写入用户事项，继续无依赖工作。禁止自动撤销保护绕过失败，不自动发布版本。

## CI 与低频操作

[CI](../../.github/workflows/ci.yml)只对面向 main 的 PR 和手动触发运行，无路径过滤，固定 job `repository-quality`。初始化通过手动运行产生真实状态后启用 Ruleset。一个 Ubuntu runner、15 分钟上限、只读 contents、checkout 不保留凭据、Action 固定完整 SHA；同一 PR 新运行取消旧运行。合并后的 main push 不重复跑同一批检查。

本地先验证、修复并集中推送；不通过反复 push 调试，不自动评论或安装 bot。远端请求有界、串行处理变更，写请求间至少一秒；遇到权限、限流或风控错误先诊断并停止相关写操作，不切换账户规避。检查名变更先让新检查成功产出，再更新保护。

配置文件、工具安装、事件触发和对应版本检查成功分别记录。只按新提交、状态变化或明确诊断需要查询结果；遇到限流遵守服务端等待要求，不通过高频轮询、重复推送或重跑相同失败消耗 CI。仓库规则不授权开启自动合并、自动审批、评论机器人或外部文档发布。

本地只设置仓库级 `core.autocrlf=false`、`pull.ff=only`、`fetch.prune=true`，不改全局身份。仓库默认 squash 并清理合并后的分支；具体期望设置见[repository-settings.json](../../.github/repository-settings.json)。安全报告见[SECURITY](../../SECURITY.md)。
