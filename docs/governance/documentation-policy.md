# 文档治理

## 信息归属

当前用户有效要求优先于旧约定。需求规定目标，设计规定实现边界，代码代表实际实现，证据说明某次执行观察；冲突必须定位并修正文档或实现，不能以日期新旧机械判断。历史材料和模板不是新的用户授权。

| 内容 | 正本 |
| --- | --- |
| 开始工作与任务导航 | AGENTS.md、docs/README.md |
| 产品行为、范围、需求编号 | docs/requirements.md |
| 模块、接口、数据与技术取舍 | docs/design.md；技术栈页只汇总与标注选型状态 |
| 开发过程与长期约束 | docs/dev-rules/ |
| 实际完成、开发后续 | docs/delivery/status.md |
| 验收计划与执行报告 | docs/delivery/、docs/evidence/ |
| 长期决定及依据 | docs/decisions/ |
| 用户决定、外部配置、授权、人工检查 | workspace USER-ACTIONS.md；产品入口仅导航 |
| 标准原始资料和哈希 | workspace docs/standards/ |

产品文档独立可读，不通过父目录相对链接形成必须存在的目录依赖。正式共享入口使用 GitHub URL；本机位置和真实配置只放忽略目录。需求编号保持稳定，标准引用记录版本和条款；“随 main 更新”只描述代码集成策略。

<a id="conflicts"></a>
## 冲突处理与责任

先看当前任务的有效指示，再按信息职责找正本；不用修改时间、措辞强弱或源工程的历史决定猜优先级。代码证明实际行为，需求/设计规定目标；冲突先区分实现缺陷、过期文档和待定需求。能从当前依据确定的修正直接完成，只有真实产品/数据/授权取舍且无法可逆隔离时才登记用户阻塞。

A 负责完整阶段计划与技术前期查证，B 负责实施和自检证据，A 集中审查并汇总有效决定；接收用户答复的 Agent 先记录原意，不等换角色才回写。职责细节只维护在[开发流程](../dev-rules/development-workflow.md#agent-handoff)，用户交流只维护在[沟通规则](../dev-rules/communication.md#agent-user)。单 Agent 兼任须标明自审，不借文件名捏造独立审核。

提案/ADR/模块规格是记录方式，draft/proposed 状态本身不产生许可节点。已授权的可逆实现和验证继续，用户未答复的默认值不写成确认。更新规则时同时核对入口、模板、计划/prompt 和验证说明，避免新旧角色或命令并存。示例、旧模板或历史报告中的“截止阶段”“等待审批”等措辞不得覆盖当前用户事项规则；明确可推导的冲突当轮修正，不再次请求用户选择。

## 登记与状态

[document-registry.json](document-registry.json)登记本仓库自有 Markdown，字段 path、kind、status、owner、scope、reviewed、basis。reviewed 仅表示本次结构/内容核对日期，不代表用户批准或产品通过。active 为当前规则，draft 为候选，reference 为来源/证据，superseded 为已替代记录；替代时注明新正本。文档状态和实现/验收状态分开，模板 active 不表示已填写，报告 reference 不授予执行权限。

workspace 中标准 PDF、OCR 和图片使用来源清单管理；OCR Markdown 不作为开发指令登记，但图片链接和文件哈希仍须检查。新增、移动和删除自有文档同步索引、登记与入链；旧稳定入口可保留短导航，不保存重复正文。

## 变更与证据

保留已有 LAB/HUB 需求编号；长期取舍使用 ADR，用户有效决定使用 A-*。用户事项使用 WS/HUB/LAB-Q/ACT/H-*，开发后续使用 LOOP-*；编号不复用。小修直接改，不为每个错字创建计划和 ADR。

证据状态仅使用 passed、failed、not-run、blocked；记录执行版本、命令、环境、输入、预期、实际、日志位置及限制。人工事项的“待复测/需重测”是工作状态，不能当作新版本已经通过。只有文档/工具验证时，不写应用启动成功、性能达标或国密验收通过。自审与独立审查分别标明。

阶段结束提炼持久结论，过期过程材料按下节整理。公开报告仅使用合成身份与脱敏结果，第三方许可证及必要来源声明保留。

## 变更规模与唯一材料

| 变更 | 最小记录与同步 |
| --- | --- |
| 错字、链接、状态纠错 | 直接改正本并检查，无需独立提案或产品确认 |
| 当前范围的局部实现/修复 | 任务、用例、真实验证；有事实变化才改对应文档 |
| 新功能或跨模块流程 | 完整阶段计划/提案，需求→设计→实现→验证→状态 |
| 公共契约、数据格式或长期规则 | ADR 或同等可追溯决定，使用方、兼容/恢复与测试同步 |
| UI 交互/主题 | 设计依据、目标状态和实际证据；主观确认状态单列 |

同阶段默认一份计划、一份交付报告；A 复核可在报告中用明确章节记录，必要独立审查文件引用它们。单 Agent 自审写明实际执行者，不因未发生独立审查留下虚假的必做交接。不同角色不另抄范围，返工只写差异。真正不同阶段各自保留计划和基点，不能为凑“一份”合并无关任务。

<a id="stage-cleanup"></a>
## 阶段开始的整理

A 在完整阶段计划中列出两项工作：按内容整理文件，检查旧阶段标签及过程材料的去向。B 随本阶段实施，A 复核；单 Agent 由当前执行者依次完成。整理是已授权阶段的一部分，不单开清理阶段，也不把发现文件等同于获得删除授权。

先用 `git ls-files` 与 `git status --short --ignored --untracked-files=normal` 盘点跟踪文件、未跟踪文件和忽略目录，依赖目录不递归展开。按本次范围检查使用方、仍有效的内容、归属和是否可恢复，不把未跟踪等同垃圾，也不为纯文档任务无界遍历大型缓存或读取无关秘密。目录级清单可先归类；候选删除和精炼必须落实到具体路径与内容判断。

<a id="file-cleanup"></a>
### 按内容选择处理方式

| 方式 | 判断 | 执行要求 |
| --- | --- | --- |
| 原样保留 | 仍在使用且内容有效，或属于用户资料、当前审查证据 | 记录保留范围，不为统一目录改动 |
| 精炼 | 仍需维护，但夹有过时描述或重复过程记录 | 保留当前结论、依据和有效入链；改名时同步使用方 |
| 提炼后删除 | 原文件已无独立用途，但结论、限制、用例或事项仍有效 | 先写入对应正本，再改入链与登记，最后删除 |
| 删除 | 无使用方、无仍需保留的内容，且归属和恢复条件明确 | 核实实际路径在授权范围，保留必要处理记录 |

是否纳入 Git 不决定去留。常见类别按下表判断，不能对整个目录一刀切：

| 类别 | 处理与前置 |
| --- | --- |
| 用户配置、数据、样本、标准原件、参考、密码材料 | 保留，不因换阶段自动移动或删除；需要调整时按实际授权与用户事项处理 |
| 当前计划、未关闭问题和未合并提交的证据 | 保留供审查/返工，不能宣布已归档后删除 |
| 已合并且过期的过程文档/制品 | 先验证合并提交确在 main 历史，提炼有效决定、限制、用例与未决项，更新入链和登记，再按授权清理；不另建阶段总结副本 |
| 仍使用的测试、脚本、依赖、最新验证产物和工具 | 保留；重命名或合并时同步调用方并验证，测试减少须有等价映射 |
| 一次性探针、审查脚本、原型及仅被它使用的依赖 | 有价值的缺陷断言迁入按能力命名的测试；仍承担验证的保留并注明退出条件，产品已替代且无使用方的才删除 |
| 无使用方的可重建日志、缓存、旧包或草稿 | 核对绝对路径在预期目录及归属，记录清理依据；不使用跨目录通配删除或 git clean -fdx |

用户配置、数据库、原始样本、标准和参考资料即使放在构建目录也不是缓存。拿不准时保留，只有确需改变它们的必要动作才按集中用户事项提出；已有明确授权仍按其范围执行，不重复询问。许可证、第三方声明、有效决定、被替代 ADR 及仍被测试使用的合成夹具不得按“阶段整理”删除。

### 已合并材料的提炼

删除已跟踪过程材料前，核对远端状态并用 `git merge-base --is-ancestor <已核对的合并提交> origin/main` 证明该提交已在主分支历史中。命令成功只证明历史可恢复，仍须判断是否有当前使用方；缺少合并或归属证据就保留。当前阶段在合并前不删除仍供审查、返工使用的材料。

提炼去向：结果/限制与 LOOP 到 status，决定到 confirmed-decisions/ADR，验收定义到需求/路线，需要用户的事到 workspace USER-ACTIONS。原来的 failed、blocked、not-run 和被测版本不能变成新的 passed。历史以 Git 保留，必要链接固定到提交；删除前修正全部入链。

<a id="destaging"></a>
### 旧阶段标签与当前状态

长期正本描述已实现、当前工作与待实现，不按审查轮次累积日志；以前已合并阶段的标签不再代替能力名称或实际状态。

| 对象 | 整理方式 |
| --- | --- |
| 状态、需求追踪、仓库地图 | 按能力和实际状态说明，注明证据版本；未完成范围保留到当前计划或后续路线 |
| 决定与 ADR | 保留稳定编号、日期、决定依据和替代关系，删除无当前用途的阶段过程叙述 |
| 用户 Q/ACT/H | 编号不含阶段；人工检查用提交或稳定包定位，未处理项按自身状态顺延 |
| 新增脚本、测试、模块与运行目录 | 默认按能力命名；旧名称仍有使用方时先列迁移映射，验证调用方后再改 |
| 旧计划、报告与归档链接 | 按材料生命周期提炼；固定到提交的历史路径可保留，链接说明表达内容和版本 |

标准版本、条款、稳定需求/用例/问题 ID、当前未退出阶段和真实证据中的被测版本必须保留。产品路线的阶段编号仍表示已承诺排期，不能靠删标签改变范围。M0 的实际完成与集成状态见[当前状态](../delivery/status.md)；其命令/路径、必要证据和 M1—M5 范围仍有使用方，不能仅因提交归并或阶段切换而删除。

<a id="stage-documents"></a>
### 计划、报告和证据的生命周期

一个阶段只维护一份计划和一份交付报告。已有适用材料直接复用；新建时默认使用不带阶段号的 `docs/delivery/stage-plan.md` 与 `docs/evidence/stage-report.md`，这是命名约定，不表示这两个文件当前已存在。下一阶段需要复用路径时，先确认原阶段已合并、有效内容已提炼，再改写计划并创建新报告；前置尚未合并时保留其独立计划/报告与依赖说明。返工和自审在本阶段报告中维护，不按角色再复制任务范围。

运行输出默认放 Git 忽略的 `artifacts/` 或 `.local/` 下独立运行目录，只把审查需要的脱敏结构化 JSON/Markdown 和关键状态截图纳入 `docs/evidence/`。每次交付新增公开证据以 5 MiB 为目标，超出时说明理由；样本不反复复制进报告目录，使用合成夹具或生成方法。旧证据在合并并完成提炼后整理，同一验收范围保留当前需要的一份结果；被未关闭问题或现行状态引用的证据先迁移引用再处理。

整理记录写入本阶段报告，包含处理路径/类别、判断与归属、提炼去向/归档提交、测试/脚本迁移映射，以及实际处理的未跟踪资料数量、大小和结果。未递归盘点的保留目录如实写“整体保留、未计数”，不能填零或宣称已清理；私有名称只在忽略的本地记录。测试数量减少必须能由映射解释，不得删除断言换取通过。

A 或单 Agent 自审者抽查提炼是否保住有效结论、未关闭事项和原测试状态，核对入链与登记。当前检查器自动验证登记/链接/路径，整理语义、旧阶段标签和退役条件由本轮审查负责；尚未实现 `currentStage` / `retireAfter` 自动淘汰检查，不写成已生效，也不添加无人消费的字段充当门禁。

## 检查

运行 `python scripts/verify.py`。新增文件先暂存以纳入 Git 跟踪清单；检查器涵盖登记、链接/锚点、越界链接、本机路径和脚本回归，不能代替语义审查、外部链接可用性、安全扫描或产品验收。
